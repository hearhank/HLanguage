# 协程 + 通道：H 语言并发模型重构

2026-08-24 项目所有者决定将 H 语言的并发模型从「OS 线程 + 四模式容器」重构为
「M:N 协程 + 单一通道类型」。

## 背景

当前并发模型（E4，2026-08-24 完成）使用：
- `spawn` → OS 线程（`std::thread::spawn`）
- `Pipe<T>` / `Tee<T>` / `Funnel<T>` / `Hub<T>` 四种通道类型
- `Mutex` 用于共享状态

该模型面临三个问题：
1. **OS 线程太重**：1 MB+ 栈，创建 ~1 µs，不适合大规模并发
2. **LLVM 后端无法实现**：OS 线程创建在 LLVM IR 中难以实现，当前 `spawn` 在原生侧
   只能 `abort`
3. **四种通道类型认知负担高**：`Tee`/`Funnel`/`Hub` 的区别对新手不友好，Go 的单一
   `chan T` 经验证明一个类型就够了

## 决策

### 并发模型：M:N 协程

| 组件 | 对应 | 说明 |
|------|------|------|
| **G（协程）** | `spawn` 创建的轻量执行单元 | 独立栈，协作式调度 |
| **M（OS 线程）** | 物理执行线程 | 已有 `std::thread::spawn` |
| **P（处理器）** | 调度资源，持有 G 就绪队列 | 每 M 一个 P，GOMAXPROCS 控制 |

**M:N 调度**：N 个协程多路复用到 M 个 OS 线程上。M 由 `GOMAXPROCS` 控制（默认
= CPU 核数）。协程在通道操作或显式 `yield` 时协作式让出。

### 通道类型：单一 `chan<T>`

用单一 `chan<T>` 替代四种容器：

| 旧类型 | 新用法 |
|--------|--------|
| `Pipe<T>` | `chan<T>.init(alloc)`（无缓冲，单写单读） |
| `Tee<T>` | `chan<T>.init(alloc)` + 多个消费者（广播） |
| `Funnel<T>` | `chan<T>.init(alloc)` + 多个生产者 |
| `Hub<T>` | `chan<T>.init(alloc)` + 多生产者多消费者 |

**API**：
- `ch.send(v)` — 发送（缓冲满或无线程接收时阻塞）
- `ch.recv() -> T` — 接收（空时阻塞）
- `ch.try_send(v) -> bool` — 非阻塞发送
- `ch.try_recv() -> ?T` — 非阻塞接收
- `ch.close()` — 关闭通道

有缓冲通道：`chan<T>.init(alloc, cap)` 指定容量。

### 调度器实现

- 在 Rust 运行时（`hc-rt`）中实现，解释器和 LLVM 后端共用
- 初始为**协作式**（无抢占），后续可加异步抢占
- 无 work-stealing（初始简化，每个 P 有独立 G 队列，可后续加）
- 通道操作（send/recv）是主要的协程调度点

## 理由

1. **轻量**：协程初始栈 ~2 KB，可创建数十万，Go 已验证
2. **LLVM 后端可行**：调度器作为运行时链接，LLVM 后端只需生成调用
3. **简化模型**：一个 `chan<T>` 替代四种类型，降低认知负担
4. **Go 成功先例**：M:N 调度 + 通道已在生产环境验证 15 年

## 代价

1. **实现工作量**：需要实现协程上下文、调度循环、可增长栈
2. **协作式调度局限**：CPU 密集型协程会阻塞其他协程（后续加抢占解决）
3. **与现有代码兼容**：`Pipe<T>` 等现有类型需要过渡期

## 备选方案

- **OS 线程 + 四种容器**（当前）：太重，LLVM 后端不支持
- **纯 async/await**：函数着色，H 已有 async 支持但未广泛使用
- **纯 OS 线程 + 通道**：OS 线程太重，不适合大规模并发
