# 四模式容器命名：Pipe 家族

2026-08-24 项目所有者确认四模式共享内存容器的命名方案。

## 背景

四模式共享内存容器（原 `OneToOne`/`OneToMany`/`ManyToOne`/`ManyToMany`）用于
线程间数据传输与共享。原命名面临三个问题：

1. **易看反**：`OneToMany` 与 `ManyToOne` 在日常阅读中频繁混淆
2. **像 ER 图**：名字听起来像数据库关系基数，而非并发原语
3. **暴露实现**：强迫用户想「谁是生产者谁是消费者」，而非「这是什么通信模式」

## 决策

使用管道配件命名体系：

| 模式 | 旧名 | 新名 | 配件隐喻 | 语义 |
|------|------|------|---------|------|
| 1 写 1 读 | `OneToOne` | **`Pipe<T>`** | 直管 | 一根管子，一头进一头出 |
| 1 写 N 读 | `OneToMany` | **`Tee<T>`** | 三通 | 一路进水多路出（三通分叉） |
| N 写 1 读 | `ManyToOne` | **`Funnel<T>`** | 漏斗 | 多路汇入一路 |
| N 写 N 读 | `ManyToMany` | **`Hub<T>`** | 集线器 | 多路进多路出 |

## 理由

1. **日常词汇**：`Pipe`/`Tee`/`Funnel`/`Hub` 都是日常英语词，零学习成本
2. **不易混淆**：四个词在拼写和发音上差异大，不可能看反
3. **管道隐喻一致**：用户自然知道它们是同一族事物，无需词法强制
4. **更短**：`Pipe<i32>` 比 `OneToOne<i32>` 短 5 个字符
5. **管道心理模型**：对齐用户「这是管道，我在这头写，有人在另一头读」的直觉

## 备选方案

- **`Chan` 家族**（`Chan`/`Chan.Fan`/`Chan.Merge`/`Chan.Mux`）：Go chan 风格，但
  `Fan`/`Merge`/`Mux` 对新手不够直观
- **Rust mpsc 风格缩写**（`Spsc`/`Spmc`/`Mpsc`/`Mpmc`）：最短但最学术，仍暴露
  实现机制
