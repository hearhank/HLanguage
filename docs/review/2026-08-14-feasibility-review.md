## 一、总评

**可行性结论**：设计整体自洽——「数据为中心 + 显式分配器 + 指针自由 + 双模式执行」是 Zig 语义与脚本体验的合理混合定位；类型系统（class 自动连续判定、元组、Table）、所有权模型（销毁责任模型）、错误处理（错误码 + 成功标记）、序列化（连续内存直映射）具备**高可行性**。风险集中在四类：**① 连续内存自动判定与栈的冲突；② 重载/返回类型/推断的交互复杂度；③ move 后原绑定语义与所有权模型的一致性；④ 脚本生成（types 元数据）的实现时序**。工程量与 README 估计一致（语言系统乐观 2–3 年，完整 4–6 年单人）。

## 二、设计问题（按严重度）

### 🔴 高严重度（影响核心语义或可实现性）

| # | 问题 | 原因分析 | 建议 |
|---|---|---|---|
| **H1** | **连续内存自动判定 → 栈溢出与拷贝性能风险** | `class Image { data: [1M]u8 }` 全值字段自动判定为连续（栈上）值类型；且用户**不可标注**存储形态（Q4 定案）。大值类型：① 栈上放置 MB 级对象 → 栈溢出；② 传参默认复制 → 性能灾难（C 的 struct 有同样问题，但 C 程序员可控 malloc；H 剥夺控制权，`box()` 是拷贝语义无法引用大对象）。 | 增加**自动判定 + 用户可覆盖**（如 `class Foo: heap` 显式堆标注）或大值类型自动堆上；至少定义「栈大小阈值」规则 |
| **H2** | **move 后原绑定仍可访问与所有权模型冲突** | Q5' 定案「move 后原绑定仍可访问（悬垂由用户负责）」——但编译器是否放行读/写？放行则 move 退化为「共享」，销毁责任转移后原绑定读取的是「他人拥有的内存」，与「所有权 = 销毁责任唯一归属」的模型张力大；不放行（报错）则与定案矛盾。文档未定义编译器行为。 | 明确编译期规则：建议 move 后原绑定**编译期标记不可用**（读/写均报错），与 Debug 悬垂标记互补；否则所有权模型失去可教性 |
| **H3** | **`==` 通用相等 vs `ICompare.eq` 语义可能不一致** | `==`/`!=` 语言内建通用（class 按身份）；用户类型实现 `ICompare` 后 `a.eq(b)`（内容）与 `a == b`（身份）结果不同——同一数据两种比较结果。编译器如何保证两者一致？未定义。 | 定义：实现 ICompare 的类型 `==` 委托 eq（或禁止同时存在两种语义）；建议 `==` 绑定 ICompare（与序比较一致），未实现 ICompare 的类型 `==` 退化为身份/逐位 |
| **H4** | **数组 → 切片隐式转换未定义，示例已隐含** | `fn sum(items: &[T])` 调用 `sum(&ints)`（ints = `[3]i32`）——`&ints` 是 `*[3]i32`，参数是 `&[T]`，类型不匹配。示例 86/87 直接这样写，但语言规范（06-02 数组与切片）只定义了显式取段 `&arr[1..3]`。**示例即规格**原则下这是规格缺口。 | 定义隐式数组切片化（`&arr` → `&arr[0..len]`）或修改示例为 `sum(&ints[0..])`；建议前者（Rust/Zig 均有类似便利） |
| **H5** | **脚本生成的「鸡生蛋」时序** | script 块需要 `types` 元数据（类型系统信息），但脚本生成的代码参与编译（可能定义类型）。语义分析在脚本执行前还是后？Q23「元数据由编译器生成注入（M2 → M3 桥）」未定义两遍法（先类型收集 → 执行脚本 → 完整分析）的时序与循环依赖处理。 | 明确两遍法：第一遍收集类型元数据 → 执行全部 script/comptime 块 → 第二遍完整语义分析；script 块不可定义新类型（或需递归迭代） |

### 🟡 中严重度（影响可用性或实现复杂度）

| # | 问题 | 原因分析 | 建议 |
|---|---|---|---|
| **M1** | **重载解析优先级矩阵未定（示例与文档矛盾）** | 87 示例注释「i32 数组走具体重载」；文档（01 §12.5/06-04）「泛型与具体重载统一参与解析，无具体优先」。两者冲突。且具体/泛型/可选参数/默认值四者组合的解析规则未定。 | 明确定义解析顺序：① 精确参数数量匹配；② 具体非泛型优先于泛型（推荐恢复）；③ 泛型按 where 验证；④ 歧义报错 |
| **M2** | **重载 + 返回类型需要「期望类型传播」** | `var x: f64 = parse("3.14")` 中 parse 的目标类型来自绑定——单向绑定推断可处理；但嵌套表达式（`expect_eq(parse(a), parse(b))`、`io.print("{}", parse(s))`）需要上下文类型（expected type）向下传播（TS 式 contextual typing）——H 的推断机制（Q-S9）只定义了局部推断，未定义期望类型传播。 | 定义期望类型传播机制（类型检查器的 expected type 通道）或限制返回类型重载仅绑定形态可用 |
| **M3** | **String = `u8[]` 别名 vs 新类型矛盾** | 文档既说「类型别名同构」（`&[u8]` 零成本互转）又说 String 有独有方法集（concat/split/find…）、实现 ICompare、`==` 内容比较——若为真别名，`Vec(u8)` 应共享全部；若 String 独有方法，则是 newtype。编译器表示不清。 | 定案：String 为**新类型（newtype）**（内部 = `Vec(u8)` 布局），`as_slice()` 显式互转；或定义「别名 + 扩展方法」机制（方法集挂到别名上，编译器特殊处理） |
| **M4** | **`IIterable(owned T)` 拥有迭代的 next 语义模糊** | `for (x) \|move item\|`「消耗元素/转移所有权」——Vec 的 next 返回 owned T 时元素是否从容器移除（O(n) 移位）？还是仅「拥有形态的视图」？实现语义不清。 | 定义：拥有迭代 = 迭代器持有容器所有权（`Vec` 被 move 进迭代器），next 返回元素所有权——容器在迭代后不可再用（与一次性迭代器语义一致） |
| **M5** | **胖指针的销毁语义未定义** | `var hp: owned *INumber = box(a, alloc)`——拥有胖指针（data + 虚表）销毁时须释放 data——运行时需知分配器/大小，胖指针需携带释放信息（alloc 引用）或约定统一分配器。文档未提。 | 定义：胖指针 data 部分携带 alloc 引用（三字宽：data/虚表/alloc）或装箱用默认分配器（销毁走默认）；建议前者（显式分配器哲学） |
| **M6** | **错误检测策略 × 双后端 = 4 组合** | Debug/Release × VM/LLVM：越界/溢出/悬垂检测行为 4 种不同——一致性测试套件需覆盖 4 组合矩阵；脚本模式 Debug 语义 vs 编译 Release 裸——`hc test` 默认脚本（Debug），编译模式 Release 下测试结果可能不同（越界不再报错）。 | 明确测试矩阵：一致性套件必须跑 `{脚本, 编译} × {Debug, Release}`；或编译模式测试默认 Debug 语义 |
| **M7** | **global 跨文件初始化顺序** | 「声明序」单文件清晰；跨文件 global 运行时初始化顺序未定义（文件顺序？依赖图？）——`global A = f()` 依赖另一文件 `global B` 时可能读未初始化值。 | 定义：跨文件 global 初始化按依赖分析排序（编译器检测循环依赖）；无依赖时按文件声明序 |
| **M8** | **Table 语法未完全落词法** | `t[i, j]` 逗号索引、`table(alloc, rows, cols, init)` 函数形态——逗号索引在 token/运算符表未定义（`a[i, j]` 与「下标+逗号」歧义）；构造形态与集合方法形态（`Vec<i32>.init(alloc)`）不一致。 | 词法/语法补 `a[i, j]` 索引规则；Table 构造统一为方法形态 `Table(T).init(alloc, rows, cols, init)` 或函数形态二选一 |
