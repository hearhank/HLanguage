## 文档结构约定

每份模块文档按层级组织：

```
## N.M 小模块
### N.M.K 语法功能点
- 具体规则要求（必须写全，规则无法自明时才给示例）
- 有效示例（```hc 代码块，仅已实现功能要求可运行）
- 错误示例（注明预期诊断）
- 状态：✅已实现 | ⚠️部分实现 | ⏳未实现·目标 | ❌已废弃
- 证据：tag1 源码路径 + 测试路径
```

- 状态标记定义：
  - ✅ 已实现——tag1 编译器按本文描述接受/拒绝，有测试或示例佐证
  - ⚠️ 部分实现——核心可解析，已知缺口（在条目内写明缺口）
  - ⏳ 未实现·目标——规范目标，实现待做（此类条目是后续任务的输入）
  - ⏸ 自举后——规范目标但排除在当前实现路线外（见「排除列表」），自举完成后启动
  - ❌ 已废弃——旧文档描述过但已移除；保留条目 + 指向替代方案，防止回潮
- 示例规则：已实现功能的**有效示例必须可编译运行**（择机收进 `examples/` 或测试集）；**错误示例注明当前实现的实际诊断文案**；未实现功能的示例标注「目标行为，待验证」。各模块示例中省略类型注解的 `var` 写法依赖 ⏸ 变量类型推断（裁决 H1，2026-08-30），校订时统一补注解。
- 禁止双写：跨模块引用一律用相对路径（如「形态见 `05-functions.md` §2.1」），不复制规则文本。

## 裁决规则（ADR-0034 补充）

对齐时四类来源（ADR / 规范描述 / tag1 代码 / 功能清单）冲突的处理次序：

1. **有 ADR 定案** → ADR 为准；代码与 ADR 不符时，本规范按 ADR 写、状态标 ⚠️/⏳，差异记入「实现待对齐清单」（后续任务池）。
2. **无 ADR、描述与代码矛盾** → 在模块文档相应条目挂「⚠️ 待裁决」块（写明双方主张 + 推荐答案），交项目所有者裁决；裁决结果回写条目，必要时补 ADR。
3. **描述了但无实现无 ADR** → 保留为规范目标，标 ⏳。
4. 一切裁决落进文档或 ADR，不允许口头定案。

## 对齐流程（逐模块循环）

1. 盘点：该模块的 ADR + 计划文档 + `tag1/` 代码 + 测试
2. 产出：模块文档草案 + 待裁决清单
3. 项目所有者裁决待裁决项
4. 定稿：更新模块文档状态为 ✅ 对齐完成；旧文档相应横幅更新
5. 进入下一模块（顺序见上表；`09` 入口模块矛盾最集中）
